# T22｜业务止损、版本回退与恢复手册

状态：依据当前代码编制，业务开关已有本地测试；正式部署的回退/备份恢复尚未演练。本手册不是已执行记录。所有操作绑定明确环境、服务、候选/回退版本和负责人，保留时间及不含凭据的证据。

## 选择正确的止损层级

| 故障 | 优先动作 | 保留/限制 |
| --- | --- | --- |
| 普通提醒或CST配置异常 | 管理员调用rollout/rollback | 隐藏普通提醒、关闭CST；安全线继续可见，数据不删除 |
| 新采集异常 | 另行设置collection_paused=true | 阻止新开卡/提示；已开始的答卷仍允许完成，不能当作全站写入冻结 |
| 通知或模型发送异常 | 停止相关平台定时器/服务入口自动调用，检查在途任务 | 标志位不等于撤回外部请求；安全通知也需单独控制发送入口 |
| 新版本接口故障 | 先止损和排空，再切回经验证兼容的版本 | 不能未经检查直接回到不支持四评的新旧混用版本 |
| 数据异常 | 隔离受影响写入、保留证据，单独恢复/修正 | 不删collection，不覆盖回执、租约、历史或同意状态“重来” |
| 凭据泄露 | 安全人员轮换对应凭据并核对调用 | 不把新旧密钥写入工单、日志或仓库；可能影响在途请求和会话，须记录范围 |

## 1. 暂停普通提醒与CST

由目标环境的有效管理员会话调用，令牌从安全运行环境读取，不粘贴到文档或命令历史。

请求逻辑（示意，不是自动执行脚本）：

```text
current = GET /v1/xg/admin/rollout
POST /v1/xg/admin/rollout/rollback
  { expected_revision: current.revision, reason: "事件编号及止损原因" }
latest = GET /v1/xg/admin/rollout
```

确认返回/回读：enable_reminder=false、enable_cst=false、emergency_stop=true；记录新revision，并用`/admin/rollout/history?scope=global&revision=...`核对作者和变更。409时重新读取并人工核对差异，不盲目覆盖较新操作。

只设置两个enable为false不能覆盖所有单案开启；紧急回滚通过emergency_stop压住普通提醒。DISSOC安全线始终可见。这个操作**不停止所有通知外发，也不暂停新采集**。

## 2. 另行暂停新采集

再次读取最新修订后：

```text
current = GET /v1/xg/admin/rollout
POST /v1/xg/admin/rollout
  { expected_revision: current.revision,
    collection_paused: true,
    reason: "事件编号及暂停采集原因" }
```

验收：新`/events/start`返回409 XG_COLLECTION_PAUSED，`/prompts/next`为空；历史读取和既有尝试的恢复/提交/放弃仍可按规则工作。所有已接受的作答、成功名额、回执、计分依据和审计保留。结案、旧事务和在途请求不能简单当作全部被冻结。

如需严格停止全部业务写入，需要另行控制入口/流量并处理在途事务；当前collection_paused不提供全库只读维护模式。

## 3. 停止外部副作用与排空

1. 在调度平台暂停通知、模型运行/恢复及不应继续执行的随访扫描。记录任务ID、暂停时间、最后一次运行和在途执行器。
2. 不再手工触发`/jobs/notification-deliver`或`/internal/llm-score`等入口；必要时按已验证的入口策略限制服务调用。仅改前端feature flag不能阻止后台任务。
3. 按实际配置核对租约及请求超时，等待并读取在途状态。当前默认通知租约60秒、LLM租约30秒，实际部署如有修改以运行配置为准；经过租约时间并不证明外部请求未发出。
4. 通知uncertain保持隔离。通过管理员任务详情和服务商证据核对后，才使用`/admin/notifications/:id/resolve`：expected_revision、outcome=accepted/not_sent、reason、evidence_reference。不得靠超时猜测not_sent。
5. LLM允许有预算的重算，但可能重复计费；不重置attempts或篡改generation以绕过预算。人工重跑使用已有审核接口并保留原因。
6. 已发送消息无法撤回，已受理调用也不能靠开关取消；保留迟到回执和发送/审计记录。

安全线的展示与发送不同：emergency_stop仍保留其展示，若要停止所有外发必须控制调度/发送通道。值班安排需在真实停发前明确，不能误把“安全线可见”当作安全消息已送达。

## 4. 兼容服务版本回退

发布前必须填写并验证：当前服务/版本、候选镜像摘要、上一个兼容版本、流量配置、函数版本和非敏感配置引用。当前这些值未确定，不能从旧README或旧cloudbaserc猜测回退对象。

1. 保存当前版本、流量、开关修订、任务状态和故障证据，先完成上述止损。
2. 检查回退版本能读取现存的42集合/版本化事件、空维度结果和新回执格式，并且不会重复发送/覆盖任务。数据库保留新数据，回退代码必须兼容它们。
3. 如首发没有四评兼容版本，应使用已演练的维护/禁用入口方案，不能把全部流量盲目切到仅支持旧PCOMS的版本并宣告恢复。
4. 由运维按已确认平台的版本/流量流程切回，核对健康、实际接口、身份、已有作答重放及私有读取。HTTP 200或进程启动不是唯一验收条件。
5. 此时继续保持采集/副作用暂停。只有完成真实烟测和负责人复核后才恢复；不要在版本回退时自动清空队列或补发历史记录。

旧SDK/模型/规则版本不能通过重新使用同一个version字段覆盖内容。旧卡片复算仍必须使用其历史引擎和依据，未知引擎应失败关闭。

## 5. 数据恢复原则

- 先确认受影响集合、时间范围、数据归属及备份可用性；RPO/RTO和备份有效性必须实测，当前未填写。
- 恢复到**新隔离集合**进行核对，不先覆盖在线数据。比对周期、成功名额、状态修订、请求回执、同意版本、来源依据及任务代次。
- 发布后新增的合法提交、撤销同意和通知受理不能因回档被遗失或重复执行。涉及合并/重放时先制定可审阅的逐项修复方案，再单独批准实施。
- 不删除xg集合回到空库，不执行T21测试清理工具处理canonical资源，不把T20合成数据当备份，不重新播种去覆盖真实用户记录。
- 修复后做只读复算和权限检查，再验证业务唯一性及队列状态；模型建议与主分分开处理。

## 6. 恢复服务检查单

- [ ] 故障原因及修复/回退版本已核对；当前镜像与确认版本一致。
- [ ] 身份、同意、当前与历史读取、既有request_id重放通过；无跨周期或越权数据。
- [ ] 新采集暂停与恢复均按最新修订执行；没有用旧请求覆盖他人操作。
- [ ] unknown/uncertain已按证据核对，未盲目重发；任务租约和代次未人工清零。
- [ ] 备份/恢复或数据修复结果已验收，合法新增数据没有丢失。
- [ ] 真实通道和告警接收人就绪，恢复后观察指标及责任人已明确。
- [ ] 逐项恢复所需的采集、普通提醒/CST与定时器，验证effective策略；不默认全量打开。
- [ ] 用户确认的发布范围/窗口仍有效，越出原范围时另行确认。

恢复不自动把安全事件标“已处理”。审计记录包括动作、环境/版本、操作者、开始/结束时间、验证证据及未关闭问题，不含明文凭据或用户答卷。
