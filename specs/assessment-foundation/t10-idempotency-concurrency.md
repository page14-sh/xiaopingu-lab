# T10｜请求幂等与真实数据库并发

日期：2026-10-25。沿用 T01 的 CloudRun + CloudBase NoSQL 路线，补充 T09 作答状态机的请求级契约。本项不部署服务，不发布正式同意书。

## 标识与请求契约

| 标识 | 作用 | 客户端行为 |
| --- | --- | --- |
| `client_event_id` | 一次填卡尝试，决定事件 ID | 开始新尝试时生成；恢复尝试沿用 |
| `request_id` | 一次 start/submit/abandon 操作 | 同一请求的重试必须沿用，修改答案或放弃原因则换新 ID |
| `submission_id` | 周期、卡片、节次/随访轮次的成功名额 | 服务端生成；多个尝试只能有一个成功占位 |

`POST /v1/xg/events` 和 `/v1/xg/events/abandon` 必须提供 `request_id`，缺失/非法返回400。开始接口可提供独立 `request_id`，不提供时使用 `client_event_id`。ID 仅允许1–128位字母、数字、下划线及短横线。可信内部调用的兼容指纹不构成 HTTP 绕过。

```json
{
  "match_id": "cycle-id",
  "event_id": "event-id",
  "request_id": "submit-uuid",
  "answers": { "s1": 6 },
  "duration_ms": 30000
}
```

示例答案仅说明字段结构，实际提交必须满足冻结题面要求。

幂等键按角色、身份、操作和 `request_id` 隔离。指纹使用规范化 JSON，对象属性顺序不影响重试；包括服务端规范化的位置、答案和客户端耗时。同一键改答案、耗时、事件、周期或放弃原因返回409 `XG_IDEMPOTENCY_CONFLICT`。新键重复提交相同已成功答案也不会改写档案或再次计分，但会记录该新操作的回执。

## 回执与状态

新增私有集合 `xg_request_receipts`，集合清单现共22个。回执只存请求摘要、归属、事件、结果状态/修订和必要错误信息，不复制原始答案、完整计分依据或身份凭据。回执、作答事件、成功名额、档案和状态审计在同一事务提交。没有事务外的“处理中”锁，也不需要清理超时锁才能重试。

- 相同请求重试：返回 `replayed=true`，不产生额外状态迁移、档案写入或成功名额。
- `status/revision`：事务读取到的当前事件状态。
- `request_status/request_revision`：原操作的结果，供客户端识别旧响应。
- 422校验失败也有持久回执。修正答案用新键；成功后重放旧失败请求仍返回原422，同时标明当前事件已经 submitted，不会回退事件。
- 结束后重放 start 返回终态及 `form=null`；未结束时重新检查当前同意和周期可填写条件。
- 未提交的权限、前置条件或存储错误回滚，不消耗请求键。已提交响应丢失则依靠同键重试查询回执恢复。
- 回执暂不设置 TTL。删除回执会缩短请求级重放保障，不能作为普通日志随意清理。

HTTP 响应仍遵循 T06：来访端不含分数、原始答案或完整计分依据。

## 冲突与不确定提交

CloudBase 适配器改为显式开启、提交和回滚事务：

1. 仅确定的 `DATABASE_TRANSACTION_CONFLICT` 自动重试；每次先尝试回滚，使用25–400ms指数退避加抖动，默认最多8次事务尝试。
2. 预算耗尽返回503 `XG_TRANSACTION_BUSY`。客户端稍后沿用原请求键重试。
3. 提交阶段的其他错误按结果未知处理，返回503 `XG_COMMIT_UNKNOWN`；不盲目自动重放业务写入。客户端沿用原键重试，若原提交已落库，将读到其回执。
4. 业务错误不自动重试；失败回滚也通过不含敏感值的观察事件记录。观察器失败不会改变提交结果。

所有重试回调只执行数据库读写，不能加入 LLM、消息发送等外部副作用。周期修订锚点、同意状态/政策锚点、成功名额和确定事件 ID 共同参与并发约束。

| --- | --- |
